# Skill authoring playbook

This is the canonical instruction file for every agent working in this project.
`CLAUDE.md` exists only to import it, because Claude Code reads `CLAUDE.md`
rather than `AGENTS.md`. Record project instructions here, not there.

This repository is an independent skill project created by Skill Smithy. Author
and validate it in place. Do not mint or import again: those commands belong to
the Skill Smithy checkout and are not installed here.

Project commands come from the exact `@neefactory/skillsmithy` development
dependency in `package.json`, not from copied Forge scripts. Run `npm install`
after minting and after changing that dependency; later clean checkouts may use
`npm ci` once `package-lock.json` has been committed.

The canonical skill source is always `skills/<skill-name>/`. Generated discovery
copies and marketplace manifests are produced by `npm run build` and must not be
edited by hand.

When enabled in `skill.config.json`, `.github/workflows/clawhub-publish.yml` is
also generated by `npm run build`. It is the one workflow file the generator
owns; other files under `.github/` remain user-owned. Configure ClawHub in
`skill.config.json`, never by editing the generated YAML.

`.claude/skills/` and `.agents/skills/` are those discovery copies. They exist so
the skill you are authoring is registered with the agent you author it in, and no
installer reads them; everything published comes from `skills/<skill-name>/`. The
Claude copy deliberately omits `agents/openai.yaml`, which is Codex product UI
metadata that Claude never reads. That file is still canonical and still
required — do not treat its absence under `.claude/` as a build error to fix.

Both directories are gitignored, because a marketplace importer that scans the
repository for skills would otherwise find three copies of `SKILL.md` instead of
one. Leave them ignored and never commit them. The manifests installers read —
`.claude-plugin/`, `.codex-plugin/`, and `.agents/plugins/marketplace.json` —
must stay committed. `npm run check` skips generated paths the repository
ignores, so a clone that has not built yet still passes, and it lists whatever
it skipped so a narrowed comparison is never reported as a complete one.

`.gitignore` is yours to extend. It is not a managed file, so migration only
appends entries a newer release introduced and never rewrites your own. Add
rules for editor state, `.claude/` project settings, hooks, scratch
directories, or anything else freely. The one rule to avoid is a broad pattern
that also covers a generated manifest or
`.github/workflows/clawhub-publish.yml` — a blanket `.github/` is the usual
way this happens. The build still writes the file and drift detection still
passes, because ignored paths are skipped, but the file never reaches the
repository an installer or GitHub Actions reads from. `npm run validate` warns
when a generated manifest or workflow that exists on disk is ignored.

An ignore rule does not untrack files committed by an older project. If
validation reports tracked discovery copies, untrack them without deleting the
local generated files:

```bash
git rm -r --cached -- .claude/skills .agents/skills
```

Then rebuild and commit the index change.

## Skill Smithy updates

`.skillsmithy/provenance.json` records the package release that created or last
migrated this project. `.skillsmithy/baseline/` contains the corresponding
managed-file baselines. Commit both; do not edit them by hand. They let a newer
package distinguish unchanged managed files from local project customizations.

Update Skill Smithy on a branch and pin the intended exact version:

```bash
npm install --save-dev --save-exact @neefactory/skillsmithy@<version>
npm run migrate -- --dry-run
npm run migrate
npm test
```

The dry-run must write nothing. Apply refreshes dependency-facing project
metadata, the destination contract and schema when safe, and all generated
adapters. It never rewrites canonical `skills/**` content. A file changed both
locally and by the newer package is a migration conflict: reconcile it manually
and rerun the dry-run rather than overwriting either side.

In `package.json`, migration manages only `name`, `version`, the Skill Smithy npm
scripts, and the tooling dependency. Everything else is yours: a `test` script
extended with this project's own evaluations, a `files` list, `private`, or any
script the contract does not define is written once if missing and never
rewritten.

`npm run validate` warns when the exact version pinned in `package.json` differs
from the release recorded in `.skillsmithy/provenance.json`. That means the
package was installed but the migration has not run yet; the managed files still
belong to the older release until you apply it.

## Starting points

Expect terse requests. Expand them into the full workflow yourself rather than
asking the user to restate it. "Write the skill", "finish this", or "get it
ready to publish" are all requests to work through the contract below, including
the interview, the validation commands, and the completion criteria the user did
not name.

Never edit imported skill content unless the user separately and explicitly asks
for edits. A project created by import carries the author's original bytes on
purpose.

If canonical files still contain TODO or placeholder text, this is an
already-created but unauthored project. Interview the user first, then author in
place. Establish:

- two or three realistic requests that should use the skill;
- situations that must not trigger it;
- expected outputs and important edge cases;
- required tools, credentials, references, and assets;
- GitHub owner/repository and publisher metadata, asked directly and never
  guessed from `git config` or the environment;
- whether ClawHub is a destination and which route the user wants: CLI,
  one-time web GitHub import, manual GitHub Actions publishing, or automatic
  publishing from a named branch;
- any ClawHub publisher handle, asked separately from the GitHub owner and
  omitted for personal publishing when the authenticated ClawHub user should
  own the skill;
- the licence, offering the three shapes under [Licensing](#licensing) with
  MIT-0 throughout as the default;
- optional discovery keywords, proposed by you under
  [Discovery keywords](#discovery-keywords) for the user to confirm.

## Publisher identity is never inherited

Publisher metadata — `owner.name`, `owner.url`, any `owner.email`, `repo`, the
licence, and any author, copyright, or footer line in `README.md` — may come
only from what the user tells you.

Never infer it from `git config`, environment variables, the Skill Smithy
checkout that created this project, or any other project on the machine. Those
sources describe someone else, not the person publishing this skill. A plausible
wrong name is worse than an unanswered one, because it ships into generated
marketplace manifests and reads as deliberate.

If the user has not supplied a value, leave the placeholder in place, omit the
copyright line rather than inventing one, and report which fields are still
unanswered. This project was created with `owner`, `repo`, and `license` reset,
so placeholders are what you will find; filling them in is a question to ask,
not a gap to close on your own.

The ClawHub publisher is separate identity. Never infer `clawhub.owner` from
`repo`, `owner.url`, or the repository organization. Omit it to publish as the
user authenticated by `CLAWHUB_TOKEN`, or write the exact user-confirmed
ClawHub organization/publisher handle.

## Discovery keywords

`skill.config.json`'s optional `keywords` array supplies the discovery terms
written into the generated Claude and Codex plugin manifests. It is the only
supported way to set them: the manifests are generated, so keywords typed
directly into `.claude-plugin/plugin.json` or `.codex-plugin/plugin.json` are
overwritten by the next `npm run build` and reported by `npm run check`.

Unlike publisher identity, keywords are not facts about a person, so propose
them yourself. Read the finished `SKILL.md` and offer three to eight terms a
user might search for — the domain, the artefacts involved, the vocabulary a
request would use — then let the user cut or add before you write them. Leave
the field out entirely if they do not want any.

The canonical skill names are always emitted, so list only terms the name does
not already cover; `npm run validate` rejects a keyword that restates a skill
name, because it changes no output. Keywords are 2-40 characters of lowercase
letters, numbers, single hyphens, or single spaces, at most twelve of them.

## Licensing

`skill.config.json`'s `license` field describes the **distributed skill**, not
the repository. It is the value written into the generated Claude and Codex
plugin manifests, which describe the installable plugin, and the plugin is
`skills/<skill-name>/`. A `LICENSE` at the project root describes the
**project** — tooling, README, evaluations, assets, CI. The two are allowed to
differ, and when they do, neither is a mistake to correct.

ClawHub publishes skills under MIT-0, so this project starts with `license` set
to `MIT-0`. Offer the user three shapes and let them choose:

1. **MIT-0 throughout** (default). `license: "MIT-0"` and a root `LICENSE`
   carrying MIT-0. Simplest, and satisfies every channel with one grant.
2. **One licence with an attribution clause**, such as MIT or Apache-2.0.
   `license` and the root `LICENSE` both name it. Say plainly that ClawHub
   publishes skills under MIT-0 before the user settles on this.
3. **Split: project licence plus MIT-0 skill.** A root `LICENSE` carrying the
   user's chosen licence, a second `LICENSE` inside `skills/<skill-name>/`
   carrying MIT-0, and `license: "MIT-0"`. The build copies the whole skill
   directory, so the skill's own licence reaches every generated discovery copy
   and every channel that consumes `skills/<skill-name>/` directly.

Shape 3 exists because the repository holds more than the skill, so its author
may reasonably want attribution on the project while the portable skill travels
freely. Do not present it as a way to keep attribution on the skill: MIT-0 is
more permissive than MIT, the grant travels with each distributed copy, and a
copy released under MIT-0 cannot be pulled back under attribution terms later.
Say that in one sentence when you offer the shape, so the user chooses it for
what it does rather than for what it sounds like.

`npm run validate` only warns when the project root has no `LICENSE` at all. It
does not read licence text, so it will not confirm that the files you wrote say
what `license` claims. That check is yours.

## ClawHub publishing

ClawHub consumes each canonical `skills/<name>/` folder. It does not consume the
Claude or Codex discovery copies, plugin manifests, project README, or root
tooling.

Set `clawhub.githubActions` in `skill.config.json` to one of:

- `"off"` — default; publish with the CLI or use ClawHub's web GitHub import.
- `"manual"` — generate pull-request dry-runs and a real publish started with
  GitHub's **Run workflow** button or `gh workflow run`.
- `"push"` — do the same pull-request dry-run and also publish automatically
  when `clawhub.publishBranch` changes under `skills/`; manual dispatch remains
  available.

For either Actions mode, `npm run build` generates
`.github/workflows/clawhub-publish.yml` using ClawHub's reusable skill workflow
from its currently documented `main` ref. Before enabling publishing, verify
that GitHub can resolve both the ref and path with `gh api --method GET
"repos/openclaw/clawhub/contents/.github/workflows/skill-publish.yml?ref=main"
--silent`. Real publishes require the repository Actions secret
`CLAWHUB_TOKEN`. Never ask the user to paste that token into chat, source,
configuration, or workflow YAML. Tell them to create the repository secret in
GitHub, or use `gh secret set CLAWHUB_TOKEN` interactively.

ClawHub's web **Import from GitHub** creates a release but does not subscribe to
future pushes. Subsequent releases happen only through another web import, the
CLI, or the generated workflow. The workflow must publish with the same owner
and folder-derived slug as the imported skill or it may be rejected or create a
different listing.

Before enabling web import, confirm that the repository is public, non-fork,
non-archived, non-disabled, owned by the signed-in GitHub account, and contains
only the canonical tracked `SKILL.md` copies. Before enabling Actions, confirm
that the workflow will be committed to the default branch and that the chosen
token can publish for the configured ClawHub owner.

Declare runtime requirements accurately under `metadata.openclaw`:

- required environment variables in `requires.env`;
- required binaries in `requires.bins` or alternatives in `requires.anyBins`;
- optional variables in `envVars` with `required: false`;
- the principal credential in `primaryEnv`;
- supported dependency installers in `install`.

ClawHub security analysis compares these declarations with the skill's actual
files. Document paid third-party accounts or services, but do not add paid-skill
or pricing metadata: ClawHub skills themselves are not paid listings. ClawHub
omits hidden paths and symlinks and enforces a 50 MB bundle limit. Run the actual
ClawHub dry-run before the first real publish because local checks cannot
reproduce every server-side security and ignore decision.

## Required workflow

1. Run `npm install` when `node_modules` or `package-lock.json` is absent, then
   author the canonical skill under `skills/<skill-name>/`. Skill names are
   lowercase, hyphenated, action-oriented, and no longer than 64 characters.
2. Write the root `README.md` as a human-facing product page. This project ships
   without one, so the file is yours to author. Keep authoring instructions and
   auxiliary documentation outside the portable skill directory. A project
   created by import may already carry a root `README.md` supplied by its
   author; expand that draft rather than replacing it silently.
3. Write the licence files the user chose under [Licensing](#licensing) — always
   one at the project root, plus one inside `skills/<skill-name>/` if they chose
   the split — and leave `license` at `MIT-0` unless they chose a single
   non-MIT-0 licence. Any copyright line names the publisher the user gave you.
   This project ships without a `LICENSE` and without CI; add a CI workflow only
   if the user wants one.
4. Keep activation guidance in the frontmatter `description`. Write the body as
   concise imperative instructions.
5. If the skill targets OpenClaw or ClawHub, declare every required credential,
   executable, configuration path, platform restriction, and installer under
   `metadata.openclaw`; check referenced environment variables against those
   declarations.
6. Create `scripts/`, `references/`, or `assets/` only when the skill needs
   them. Test every added script.
7. Update `agents/openai.yaml` so its display name, 25-64 character summary, and
   `$skill-name` default prompt match `SKILL.md`.
8. Replace the publisher placeholders in `skill.config.json` using the interview
   answers only. Leave any field the user has not answered as a placeholder and
   say so. Add `keywords` here if the user confirmed any under
   [Discovery keywords](#discovery-keywords), and omit the field otherwise.
9. Configure `clawhub.githubActions` only from the user's chosen publishing
   route. For `"push"`, write the confirmed `publishBranch`; write
   `clawhub.owner` only when the user supplied that ClawHub handle.
10. For substantial skills, keep evaluation cases and fixtures in a root `evals/`
   directory, not inside the portable skill. Nothing scaffolds or validates
   `evals/`; it is a suggested location, so create it only when the skill
   warrants evaluations. Forward-test realistic requests without leaking the
   expected answer into the test prompt.
11. Audit every example against every mandatory rule before building. Identify
   contradictions, prohibited terms, output-format conflicts, and unclear
   precedence; ask the user which instruction wins. Forward-test at least one
   single-input and one multi-input case. For output-only skills, verify that
   examples contain no introductions, labels, or explanations.
12. Run `npm run build`, `npm test`, then `npm run doctor`. If ClawHub Actions
    are enabled, report the required `CLAWHUB_TOKEN` repository-secret setup and
    the manual dispatch or push behavior; never claim the secret is configured
    unless that was verified.

## Single skill versus bundle

Default to one skill per repository. If several skills must always be installed,
versioned, and maintained together, create the first extra skill with:

```bash
npm run add-skill -- <skill-name> --bundle <plugin-name>
```

After bundle mode is active, add further cohesive skills with:

```bash
npm run add-skill -- <skill-name>
npm run add-skill -- --from <path>
```

Do not switch to bundle mode merely because skills are related. If users may
install or release them separately, use separate repositories.

## Validation commands

- `npm run build` generates exact marketplace and project-discovery adapters
  plus the optional ClawHub GitHub Actions workflow.
- `npm run validate` checks config, portable YAML, skill naming, UI metadata,
  OpenClaw/ClawHub runtime declarations and bundle preflights, bundle rules,
  tracked discovery-copy duplication, and generated manifest/workflow schemas,
  and warns when the declared licence has no matching `LICENSE` file or when a
  generated manifest or workflow is gitignored.
- `npm run check` builds in isolation and byte-compares generated output without
  mutating the working tree, and lists any generated path it skipped because the
  repository ignores it.
- `npm run migrate -- --dry-run` previews a Skill Smithy package migration
  without writing; `npm run migrate` applies a conflict-free migration and
  regenerates adapters.
- `npm test` runs validation and drift detection.
- `npm run doctor` reports publishing prerequisites and commands.

`mint` and `import` exist only in the Skill Smithy package/template entry point.
This project exposes its dependency-provided tooling through `add-skill`,
`build`, `validate`, `check`, `doctor`, and `migrate`.

## Completion criteria

Leftover scaffold text is reported as a warning, not an error, so a green
`npm test` is necessary but not sufficient. Judge readiness yourself: do not call
a skill publishable while TODO or example placeholder text remains, the root
README is missing or does not describe this product, configuration still names
`your-handle/your-repo`, publisher metadata was guessed rather than answered by
the user, the project has no root `LICENSE`, the licence files do not carry the
shape the user chose under [Licensing](#licensing), scripts are untested,
generated output is stale, or `npm test` fails.

When ClawHub is a destination, do not call the skill publishable while runtime
requirements are undeclared, a conflicting skill-local licence remains
unresolved, the bundle exceeds ClawHub's limit, discovery copies are tracked,
or the selected publishing route lacks its documented owner/token/default-branch
setup.
